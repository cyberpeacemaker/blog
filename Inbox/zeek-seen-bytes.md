把「檔案大小」當成抓駭客的關鍵線索，在威脅獵殺中被稱為**體積特徵分析（Volumetric Profiling）**。這就像偵探在泥地上看到腳印，雖然看不清鞋底花紋，但光看腳印的深淺，就能斷定嫌犯是個體重 90 公斤的壯漢，而不是 50 公斤的瘦子。

要徹底理解為什麼「~6 MB」和 `seen_bytes` 能讓分析師一秒鎖定 Caldera Sandcat，我們需要剖析 **Go 語言的編譯特性** 以及 **網路日誌的底層計數機制**。

## 1. 為什麼 Go 語言編譯的程式是個「大胖子」？

Caldera 的 Sandcat Agent 是用 **Go (Golang)** 寫的。現代駭客與紅隊非常喜歡用 Go 語言來開發惡意軟體，因為它跨平台方便（寫一次就能編譯成 Windows, Linux, macOS 版本），而且對多執行緒併發處理極強。

但 Go 語言有一個代價：**編譯出來的二進位檔案體積非常大。**

為什麼一個小小的遠端控制木馬，動不動就要 6MB 起跳？

- **靜態鏈結（Static Linking）：** 像 C/C++ 寫的程式，很多功能會去調用 Windows 內建的動態鏈結庫（`.dll`）。但 Go 語言預設會把所有需要的第三方套件、依賴庫，通通「打包封裝」進同一個 `.exe` 檔案裡。
    
- **內建「廚房與沙發」— Go Runtime：** Go 程式在執行時不需要依賴目標主機的環境，因為它把整個作業環境（Runtime）都帶在身上了，包含垃圾回收機制（Garbage Collection, GC）、協程排程器（Goroutine Scheduler）等。一個什麼都不寫的 Go 語言 "Hello World" 程式，編譯出來通常就要 1MB 到 2MB。
    
- **功能加總：** Sandcat 作為一個 C2 Agent，裡面還要塞進 HTTP/HTTPS 通訊模組、Base64 解碼器、指令執行接口等。這些代碼堆疊起來，**6MB 上下正是 Go 語言開發的輕量級惡意程式在未經特殊壓縮（如 UPX 殼）時的「標準體重」**。
    

## 2. `seen_bytes`：照妖鏡般的網路真實數據

在 HTTP 日誌中，其實有一個欄位叫 `Content-Length`（內容長度），那是伺服器主動告訴客戶端的檔案大小。**但是，駭客非常容易偽造這個欄位。** 駭客可以在 HTTP Header 裡寫 `Content-Length: 500`（假裝自己只有 500 位元組），但背後卻源源不絕地傳送了 6MB 的檔案。

這時，Zeek 日誌裡的 `seen_bytes` 就發揮了「照妖鏡」的作用：

- `seen_bytes` 不是聽信伺服器的一面之詞，而是 **Zeek 在網路線路上，眼睜睜看著 TCP 流量流過去，邊數邊記錄下來的「實際位元組總數」**。
    
- 當日誌顯示 `seen_bytes: 6,072,904` 時，代表不論攻擊者怎麼在 Header 裡玩花樣，網路線上就是確實跑過了 6,072,904 流量的檔案資料。
    

## 3. 實戰破案：如何用「體重」秒殺假假設？

我們回頭看調查報告中的 **競爭假設 H-C**：「Curl 或是其他良性的工具才是那個 Agent」。

分析師利用體重特徵，拉出了一張對比表，高下立判：

|**工具名稱**|**常見預期體積 (Windows x64)**|**調查日誌中的 seen_bytes**|**結論判定**|
|---|---|---|---|
|**`curl.exe`** (良性工具)|約 **400 KB - 500 KB**|6,072,904 ❌|體重不符，直接排除 H-C|
|**`certutil.exe`** (內建工具)|約 **1.5 MB - 2 MB**|6,072,904 ❌|體重不符，排除|
|**`Sandcat Agent`** (Go 編譯)|約 **5 MB - 7 MB**|**6,072,904** (約 6.07 MB) ⭕|**完美吻合，高度懷疑！**|

這就是高階分析師的靈活之處。他不需要等到把整個檔案還原、丟進沙箱（Sandbox）去跑行為分析，光是在流量日誌裡看到 `application/x-dosexec`（是個程式）加上 `6.07 MB`（是個 Go 寫的程式重量），他就已經在心中對嫌犯開了拘捕令。

### 進階延伸：如果攻擊者用了「減肥術」呢？

經驗豐富的攻擊者也知道 6MB 的 Go 二進位檔案在網路上太扎眼了，所以他們有時會使用 `strip` 指令刪除偵錯資訊，或者使用 **UPX 壓縮殼**。一個 6MB 的 Sandcat 經過 UPX 壓縮後，體積可能會暴富縮小到 **2MB 左右**。

如果今天日誌裡出現的是 2MB，分析師可能就需要結合別的特徵（例如檢查 PE 檔案的節區名稱是否有 `UPX0` / `UPX1`）來做進一步判斷了。而在你給出的這個案例中，紅隊顯然使用了「原汁原味」未壓縮的 Sandcat，這才留下了這個完美的 6.07MB 簽名。

既然提到了這個檔案大小和後續的橫向移動，在你們的環境中，是否有針對這種「異常大體積的可執行檔下載」設定自動化的排程告警（例如阻斷或隔離），還是目前主要仰賴事後的人工獵殺？
