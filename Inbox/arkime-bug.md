## Part 2：Arkime 解析器 bug 的「狀態未重置」是什麼意思？

這可以用一個「工廠包裝員」的故事來比喻。

在 HTTP Keep-Alive 機制下，瀏覽器跟伺服器建立**一次** TCP 連線（就像鋪設了一條傳送帶），然後在這條傳送帶上源源不絕地傳送多個 HTTP 請求與檔案（下圖的 Task 1, 2, 3）。

Plaintext

```
[ TCP 連線（傳送帶） ] ────────────────────────────────────────────────────────►
   ┌──────────────┐      ┌──────────────┐      ┌──────────────┐
   │ Task 3 (File)│      │ Task 2 (File)│      │ Task 1 (File)│
   └──────────────┘      └──────────────┘      └──────────────┘
```

而 Arkime 的 HTTP 解析器就像是站在傳送帶旁邊的「包裝檢驗員」，他的工作是：

1. 看到 Task 1 過去，**拿出一張白紙**，開始計算 Task 1 的 MD5。
    
2. Task 1 結束，把算好的 MD5 寫入資料庫（`http.md5` 欄位）。
    
3. **關鍵動作：把手上的白紙丟掉，換一張新的白紙（這就是「重置/釋放狀態」）。**
    
4. 看到 Task 2 過去，開始算 Task 2 的 MD5。
    

### 發生 Bug 時，檢驗員怎麼了？

在某些有缺陷的 Arkime 版本中，當 TCP 傳送帶一直沒停（Keep-Alive 連線持續接著），這個檢驗員在做完第 1、2 個任務後，**大腦當機（Parser 狀態卡死），忘記執行「步驟 3（重置狀態）」**：

- **狀況 A（累加）：** 他沒有換新紙，繼續把 Task 3 的資料疊加在 Task 1、2 的資料後面一起算 MD5。這導致算出來的雜湊值完全是垃圾數據。
    
- **狀況 B（罷工）：** 他發現系統狀態異常（例如找不到 Task 3 的開頭），於是決定**直接罷工**。後續傳過去的 Task 3、Task 4，他看都不看，也完全不幫忙算 `http.md5` 了。
    

這就是所謂的 **"silently drops late keep-alive tasks"**（無聲無息地丟棄後半段的 Keep-Alive 任務）。雖然封包確實有經過網路，但 Arkime 的應用層解析器（HTTP Parser）因為狀態卡死，在資料庫裡直接留白，讓你以為後面沒有傳輸任何檔案。
